# 评分与红线规则 V1.4

本版本修复复杂红线漏判与岗位标题误导风险；语义模型负责证据与职责分类，Python 的 `decide_score` 是原生/Hy4 共用的最终约束。通用JD事实层与画像相关判断层分离；绝不根据某7家公司名称硬编码分数。

## 1–5 分语义

- **1 分**：命中明确的一票否决条件。
- **2 分**：核心职责或要求明显不匹配。
- **3 分**：部分匹配，存在较大缺口或需核实。
- **4 分**：较匹配，少量技能需要补充。
- **5 分**：高度符合求职方向和能力背景，且没有明显硬伤。

## Python 最终约束

1. 每个画像红线都必须由模型评估一次，缺少或重复均失败；没有硬排除条件的用户可使用空红线列表，对应空评估列表，不触发硬否决。
2. 红线 `true` 必须附 OCR 原文证据，否则该项失败，不接受模型口头结论。
3. 至少一个有效 `true` 红线 → `hard_reject=true`，最终分为 1。
4. 没有有效红线但模型给 1 分 → 最终分修正为 2。
5. 根据**当前用户画像**生成 `role_fit`（aligned/partial/mismatch/unknown）：若核心实际工作方向明显 mismatch，最终分最高2分，但**不是1分硬否决**；技能缺口或单纯要求资历较高不应自动判断mismatch。
6. 当前用户画像显式列出的 `soft_risk_rules` 若命中，按配置的 `max_score` 降档（2–4）；不对其他画像生效。其余模型2–5分保留；4–5分至少两条可追溯匹配点。
7. `capability_fit` 对照当前画像判断能力深度：`major_gap` 需要至少两条不同OCR原文，且其中技术/工程深度信号至少同时覆盖任职要求与职责/加分项，Python才将最终分最高限制为3；薪资、经验不限、强烈用词、单条加分项、第一条位置本身不能触发降档。重大能力差距不是硬红线，不能自动判1。另一画像具有相关经验时，可得高分。
8. `unknown` 不触发硬否决；需保存待确认条件。字段、岗位职责、技能强制程度、匹配点、缺口、红线、软风险的证据必须是 OCR 逐字子串。
9. `profile_sha256` 必须与当前画像一致；同一ID但内容变动也必须重新评分。老版V1.1的JD在V1.2需补充事实层，OCR可复用。
10. 可选的 `structured_condition` 仅当用户确认且事实层明确符合时自动补判遗漏的硬红线。`required_skill`不触发`preferred`或`alternative`。

11. **抗压偏好仅对当前画像生效**：`stress_tolerance=weak` 且JD事实层提取到明确针对候选人的高抗压/快速成长/陡峭成长曲线要求并有OCR证据，最终分额外减1（最低2分，硬红线仍1分）；strong/average/未指定不扣。不得把公司业务“增长迅速”当成候选人的抗压要求，也不得将弱抗压升级成硬红线。

## 防误杀

- “了解 C++ 优先”不等于“必须熟练 C++”。
- “参与算法团队”不等于“主要从事底层算法研发”。
- “3 年以上优先”不等于“3 年以上必须”。
- 简历没有写某项技能不等于用户没有该能力。
- “业务Leader需求转成可上线Agent”不等于纯项目管理；“Agent框架/Runtime开发”不等于普通Agent应用。
- “模型协作”不等于核心模型算法职责；混合岗需要按职责证据分别判断。
- 仅提及 Java、微调、测试、数据分析等词，不足以证明其主要职责命中排除。
- 截图未写外包，不可自行认定外包；可列待确认。

## 示例画像与原 Demo 的兼容性

示例画像可覆盖 Agent/RAG/LangGraph/Python 大模型应用、真实业务落地、AI 评测等偏好，以及原 Demo 的 Java 主后端、C++ 核心门槛、底层算法、外包驻场等排除规则。真实使用时必须来自用户聊天确认，不能默认套用示例。
